# UI Patterns

This section documents **UI patterns** — reusable interaction and layout
patterns composed from Fluent UI v9 and the Axis Fluent component packages.

They are deliberately called **patterns**, not **components**. A *pattern* is a
worked example that lives in this Storybook (in the examples app) and can change
freely. A *component* is a published, versioned package under
`@axiscommunications/fluent-*` that other teams install and depend on. Patterns
are where an idea is explored and proven; components are what a pattern becomes
once it is stable enough for others to build on.

## Who this is for

- **Designers** — explore the patterns as the default building blocks for new
  experiences. Each one shows the real, themed components in action, so what you
  see here is what ships.
- **Developers** — find the code behind each pattern, reuse it, and understand
  what it takes to turn a pattern into an installable package.

## Where things live in the repo

**Patterns** — the staging area:

- **Location:** `examples/src/storybook/ui-patterns/`
- **Published:** no — part of the private `examples` app
- **Stability:** free to change, no versioning
- **Use it:** copy or reference the pattern

**Components** — the stable library other apps depend on:

- **Location:** `components/<name>/`
- **Published:** yes — `@axiscommunications/fluent-*` on the registry
- **Stability:** versioned; the public API is a contract
- **Use it:** `npm install @axiscommunications/fluent-<name>`

## Using the patterns

- Browse the patterns in the sidebar and use the **Controls** to explore props
  and variants.
- Switch the **theme** toolbar to preview a pattern across the Axis light/dark
  themes — patterns are built with design tokens, never hard-coded colors.
- Apply them as the **default approach** for new experiences: you get
  consistency, predictable behavior, accessibility, and a faster start.
- Need something that doesn't exist yet? Check the published packages and this
  section first. If it's missing, this is where it begins.

## From pattern to component

When a pattern is reused enough to be worth sharing as a package, it gets
promoted into `components/`. The bar for that move is two things being true:

- **Design-ready** — the experience is settled: behavior, layout, tokens,
  accessibility, and the set of variants.
- **Dev-ready** — the **public API is a contract**: a clean prop shape, the
  expected peer dependencies, unit tests, a docs README, and a barrel export.
  This is a separate step from "looks done", because once it's published other
  apps depend on the API and breaking it is costly.

### Want to promote a pattern? Here's how

1. **Check it's a good fit.** The pattern should be reusable and self-contained,
   depend only on `@fluentui/react-components` / `@fluentui/react-icons` as
   peers, and fill a gap that isn't already covered by an existing package —
   check for overlap with what's already published before starting.
2. **Talk to the [Design System Group](#working-with-the-design-system-group)
   early**, before you write the package. They confirm design-readiness and can
   flag naming/API concerns before they're baked into a public contract.
3. **Scaffold the package** under `components/<name>/`, mirroring an existing
   small package (`side-navigation` is a good template):
   `src/index.ts` (barrel export), `<name>.tsx`, `<name>.types.ts`,
   `<name>.styles.ts`, `<name>.spec.tsx`, plus `package.json`, `tsconfig.json`,
   `tsconfig.build.json`, `vitest.config.ts`, and `depcheck.yml`.
4. **Move the implementation over**, refining the API as you go: trim any
   oversized prop surface, and replace things like brittle string
   interpolation with formatter callbacks so the component works for
   internationalized consumers.
5. **Meet the dev-ready checklist** before opening a PR:
   - `package.json` has **no** `"private": true`, is named
     `@axiscommunications/fluent-<name>`, and matches the shared monorepo
     version.
   - `exports` maps `.` to `./lib/index.d.ts` and `./lib/index.js`; `files` is
     `["lib"]`.
   - `peerDependencies` (not direct dependencies) declare the Fluent and React
     packages the component needs.
   - `publishConfig.registry` points at GitHub Packages, matching every other
     published package.
   - A `docs/README.md` covers install, usage, a props table, and
     accessibility notes.
   - At least one `*.spec.tsx` unit test using vitest + Testing Library.
   - `pnpm build`, `pnpm --filter @axiscommunications/fluent-<name> lint`, and
     `test` all pass.
6. **Open a PR against `main`** using a
   [conventional commit](https://www.conventionalcommits.org/) message (e.g.
   `feat(my-component): add MyComponent package`). `CODEOWNERS` routes the
   review to the maintainers team automatically.
7. **Update the story** that used the pattern to import from the new published
   package instead of the local composite, so the docs and the real package
   stay in sync.

A promoted component keeps the same conventions as the rest of the library:
Fluent peer dependencies, `makeStyles` + design tokens, `axis-<Name>` class
names, types and styles split into their own files, and a `*.spec.tsx` test
suite. For the complete step-by-step recipe (including the `advanced-data-grid`
private-package precedent for patterns that are structurally ready but not yet
publishable), see
[`.github/skills/promoting-composites-to-components/SKILL.md`](https://github.com/AxisCommunications/fluent-components/blob/main/.github/skills/promoting-composites-to-components/SKILL.md)
in the repo.

## Working with the Design System Group

The Design System Group (DSG) stewards the global patterns and components in this
library and keeps them aligned with the Axis Design Guidelines. Think of DSG as
an **extension of your team** rather than a gatekeeper — we are available
throughout the work, not only at a final review.

We're glad to help with:

- **Compliance** — checking that a pattern or component follows the Axis Design
  Guidelines across UX, UI, accessibility, and tokens.
- **Design** — shaping a new pattern or component, or refining an existing one.
- **Evaluating updates** — reviewing proposed changes to existing components and
  assessing new ones, whether they ship today or are still on the horizon.

Reach out early — even before you start building. We can point you to something
that already exists, share the conventions, and help you avoid rework later.

## Two layers: Figma and code

A pattern usually exists in two places, and the link between them is kept by
**naming and documentation**, not by tooling:

- **Figma** (for designers) — the design representation: shapes, tokens, behavior.
- **Code** (for developers) — the Fluent UI React implementation: the real thing.

**Code is the source of truth, and this Storybook documents the code.** Every
story renders the actual component, so the docs and the implementation can't
drift apart. Keep the names matching between Figma and code — if they diverge,
the link between design and implementation breaks.

## Ownership

Each component is owned by the team that maintains it, enforced in the repo
through path-based `CODEOWNERS` — so changes to a component require a review from
its owners, and different components can have different reviewers. Ownership can
move to another team if they become the main maintainer over time.
